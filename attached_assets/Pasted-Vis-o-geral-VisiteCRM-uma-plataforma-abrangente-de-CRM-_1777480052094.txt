Visão geral
VisiteCRM é uma plataforma abrangente de CRM SaaS desenvolvida para agências de turismo brasileiras especializadas em excursões em grupo e viagens personalizadas. Seu objetivo principal é agilizar as operações dessas agências, oferecendo multilocação, acesso robusto baseado em função e recursos abrangentes para gerenciamento de viagens, assentos, reservas e finanças. A plataforma também inclui rastreamento financeiro, pipeline de vendas Kanban, ferramentas de comunicação, recursos de automação, programas de fidelidade, sistema de indicação, medição de NPS (Net Promoter Score) e análises avançadas dos dados. O VisiteCRM pretende ser a principal espinha dorsal operacional das agências de turismo brasileiras, aumentando a eficiência, o envolvimento do cliente e o crescimento dos negócios em um segmento de mercado especializado (excursões).

1. Visão Geral
VisiteCRM é um CRM SaaS multi-tenant para agências de turismo brasileiras especializadas em excursões em grupo. O sistema gerencia o ciclo completo: viagens → assentos → reservas → pagamentos → pós-venda.

Funcionalidades-chave:

Gestão de viagens e assentos com mapa visual
Reservas com sincronização multi-origem (agência, vendedor, loja pública)
Pipeline de vendas Kanban
Pagamentos integrados (PIX, cartão, boleto)
Automações (Se X → fazer Y)
NPS, marketing, fidelidade e analytics
Painel SuperAdmin com métricas SaaS (MRR, Churn, LTV, CAC)

4. Modelo de Banco de Dados Multi-Tenant
Todas as tabelas multi-tenant possuem tenant_id obrigatório. Valores monetários em centavos (integer).

4.1 Schemas Drizzle — Tabelas Core
// ============================================================
// packages/db/src/schema/tenants.ts
// ============================================================
import { pgTable, uuid, varchar, text, timestamp, boolean, integer, pgEnum } from 'drizzle-orm/pg-core';

export const tenantStatusEnum = pgEnum('tenant_status', [
  'trial', 'active', 'suspended', 'cancelled'
]);

export const tenants = pgTable('tenants', {
  id: uuid('id').defaultRandom().primaryKey(),
  name: varchar('name', { length: 255 }).notNull(),
  slug: varchar('slug', { length: 100 }).notNull().unique(),
  cnpj: varchar('cnpj', { length: 18 }).unique(),
  email: varchar('email', { length: 255 }).notNull(),
  phone: varchar('phone', { length: 20 }),
  logoUrl: text('logo_url'),
  status: tenantStatusEnum('status').default('trial').notNull(),
  planId: uuid('plan_id').references(() => plans.id),
  stripeCustomerId: varchar('stripe_customer_id', { length: 255 }),
  stripeSubscriptionId: varchar('stripe_subscription_id', { length: 255 }),
  onboardingCompleted: boolean('onboarding_completed').default(false),
  trialEndsAt: timestamp('trial_ends_at'),
  createdAt: timestamp('created_at').defaultNow().notNull(),
  updatedAt: timestamp('updated_at').defaultNow().notNull(),
});

  excludes: text('excludes'),
  itinerary: text('itinerary'),
  createdBy: uuid('created_by').references(() => users.id),

5. Multi-Tenancy — 3 Camadas de Proteção
A segurança multi-tenant opera em 3 níveis independentes. Mesmo que uma camada falhe, as outras protegem.


Requisição HTTP
      │
      ▼
┌──────────────────────────┐
│  CAMADA 1: Middleware     │  Express resolve tenantId via Clerk
│  req.tenantId = X         │  Verifica status (trial/ativo/suspenso)
│  Rejeita se inválido      │  Cache de 5 min por clerkId
└───────────┬──────────────┘
            │
            ▼
┌──────────────────────────┐
│  CAMADA 2: Drizzle        │  withTenant(db, X, fn)
│  SET LOCAL tenant_id = X  │  tenantScope() no WHERE automático
│  Código nunca esquece     │  Helper forçado em toda query
└───────────┬──────────────┘
            │
            ▼
┌──────────────────────────┐
│  CAMADA 3: PostgreSQL RLS │  USING (tenant_id = current_tenant_id())
│  Última barreira          │  Mesmo com bug → banco bloqueia
│  SuperAdmin bypassa       │  Via role visitecrm_superadmin
└──────────────────────────┘
5.1 Camada 1 — Middleware Express
Arquivo: apps/api/src/middleware/tenant.ts

Responsabilidades:

Resolver tenantId a partir do clerkId do usuário autenticado
Verificar se o tenant está ativo (trial válido, não suspenso, não cancelado)
Injetar req.tenantId, req.userId, req.userRole, req.isSuperAdmin
Cache em memória (TTL 5 min) para evitar query a cada request
Para a loja pública: resolveStoreTenant resolve o tenant pelo slug na URL.

5.2 Camada 2 — Drizzle Tenant-Scoped Client
Arquivo: packages/db/src/tenant-context.ts


// Toda operação multi-tenant DEVE usar withTenant()
export async function withTenant<T>(
  db: Database,
  tenantId: string,
  fn: (tx: Database) => Promise<T>
): Promise<T> {
  return await db.transaction(async (tx) => {
    // Define tenant_id na sessão PostgreSQL (para RLS)
    await tx.execute(sql`SET LOCAL app.current_tenant_id = ${tenantId}`);
    return await fn(tx as unknown as Database);
  });
}
Helper adicional: tenantScope() adiciona WHERE tenant_id = X automaticamente.

5.3 Camada 3 — PostgreSQL RLS
Aplicado em todas as tabelas multi-tenant:

users, trips, bus_models, seats, customers, reservations, payments, pipeline_stages, audit_logs, nps_responses, automations, categories, campaigns, store_settings
Policies: SELECT, INSERT, UPDATE, DELETE — todas filtram por current_tenant_id().

SuperAdmin: Role visitecrm_superadmin com policy USING (true) para acesso total.

Índices de performance: Compostos em (tenant_id, campo_mais_usado) para cada tabela.

6. Fluxo Completo de Reserva com Sincronização
Este é o coração do sistema. Toda reserva, independente da origem, passa pelo mesmo service centralizado.

6.1 Origens da Reserva
Origem	Contexto	Source
🏢 Agência	Admin cria pelo painel	agency
👤 Vendedor	Vendedor cria pelo app/painel	seller
🛒 Loja Pública	Cliente faz auto-reserva	store
📋 Importação	CSV ou API externa	import
6.2 Fluxo — Ponto Único de Entrada

QUALQUER ORIGEM → reservation.service.ts → createReservation()
Sequência dentro de uma única transação:

1. Upsert Cliente (criar ou vincular)
      ↓
2. Reservar Assentos (lock otimista — verifica disponibilidade)
      ↓ falha? → Erro: "Assentos indisponíveis"
3. Criar Reserva (status: PENDING, code: VCR-2026-XXXXX)
      ↓
4. Mover no Pipeline → stage "Nova Reserva"
      ↓
5. Criar Cobrança (PIX / Cartão / Boleto / Manual)
      ↓
6. Atualizar stats do Cliente
      ↓
7. Audit Log
      ↓
8. Emitir Evento: reservation:created
6.3 Após Criação — Fila BullMQ
O evento reservation:created dispara jobs assíncronos:

✉️ E-mail de confirmação de reserva
📱 WhatsApp (se configurado)
📄 Gerar PDF do comprovante
🤖 Executar automações ativas para o trigger reservation_created
6.4 Webhook de Pagamento — Fluxo de Confirmação

Gateway confirma pagamento (webhook)
      ↓
payment.service.ts → confirmPayment()
      ↓
1. Atualizar Payment (status: PAID, paidAt)
      ↓
2. Atualizar Reservation (status: CONFIRMED, paidAmount += valor)
      ↓
3. Confirmar Assentos (status: CONFIRMED)
      ↓
4. Mover no Pipeline → stage "Pago"
      ↓
5. Atualizar Cliente (totalTrips++, totalSpent += valor)
      ↓
6. Audit Log
      ↓
7. Emitir Evento: payment:confirmed
      ↓
Jobs: E-mail "Pagamento OK" + Recibo PDF automático

7. Sincronização Global de Dados
7.1 Problema
Quando uma reserva é criada/atualizada por qualquer via, as seguintes telas precisam refletir a mudança imediatamente:

Tela	O que atualiza
Dashboard da Agência	Contadores, receita, ocupação
Mapa de Assentos	Status do assento (disponível → reservado → confirmado)
Pipeline Kanban	Card move de coluna
Página de Reservas	Nova linha na lista
Página de Clientes	totalTrips, totalSpent
Perfil do Cliente	Histórico de reservas
Dashboard do Vendedor	Suas vendas
Analytics	KPIs recalculados
7.2 Solução — Arquitetura de Sincronização
Camada	Tecnologia	Função
Service Layer	EventEmitter interno	Toda mutação emite evento tipado
Backend → Frontend	Server-Sent Events (SSE)	Push de atualizações em tempo real
Cache do Frontend	React Query (TanStack Query)	Invalidação automática por evento
Estado Local	Zustand	UI otimista + estado temporário
7.3 Fluxo de Sincronização

1. Service executa mutação no banco (dentro de withTenant)
      ↓
2. EventBus emite evento tipado:
   - reservation:created { reservationId, tripId, customerId }
   - payment:confirmed  { paymentId, reservationId }
   - seat:updated       { seatId, tripId, status }
   - customer:updated   { customerId }
      ↓
3. SSE Controller escuta eventos e envia para clientes conectados
   (filtrado por tenantId — cada tenant só recebe seus eventos)
      ↓
4. Frontend recebe evento via EventSource:
   - React Query invalida queries relacionadas:
     queryClient.invalidateQueries(['trips', tripId])
     queryClient.invalidateQueries(['reservations'])
     queryClient.invalidateQueries(['seats', tripId])
     queryClient.invalidateQueries(['customers', customerId])
     queryClient.invalidateQueries(['pipeline'])
     queryClient.invalidateQueries(['dashboard'])
      ↓
5. Componentes re-renderizam automaticamente com dados frescos

Resumo das Decisões Técnicas
Decisão	Escolha	Motivo
ORM único	Drizzle	Type-safe, performático, sem conflito
Auth único	Clerk	Pronto, seguro, multi-tenant nativo
Multi-tenancy	tenant_id + RLS + Middleware	3 camadas = zero vazamento
Sincronização	EventBus + SSE + React Query	Simples, eficiente, sem WebSocket complexo
Pagamentos	Adapter Pattern	Trocar gateway sem mudar lógica
Filas	BullMQ + Redis	E-mails, PDFs, webhooks, relatórios
Reserva	Service Layer único	Toda origem passa pelo mesmo código
API Client	OpenAPI + Orval	Hooks auto-gerados, zero inconsistência
Estado frontend	Zustand + React Query	Local vs servidor separados
Princípio fundamental: Todo dado entra por um service centralizado, que executa em transação atômica, emite eventos tipados, que disparam sincronização automática em todas as telas. Não importa se a reserva veio da agência, do vendedor ou da loja — o fluxo é idêntico.
