---
name: Vercel canceled Git deployments
description: Recovery when the linked Vercel project cancels an automatic Git deployment before it builds
---

**Rule:** An automatic Vercel deployment can be marked `CANCELED` before build even when the commit changes published files. Do not infer a source or ignore-command failure from that status alone. For an explicitly requested publish, create a fresh production deployment from the exact GitHub source SHA; `forceNew=1` bypasses deployment deduplication. Redeploying the canceled deployment by its `deploymentId` may be rejected. If the automatic deployment is canceled because the commit signature is unverified, treat that as a security gate: only use a manual deployment that bypasses it after the user explicitly authorizes that one-off. For this linked GitHub project, `gitSource.type="github-limited"` with `repoId` failed as `git_info_fail`; the working request used `type="github"` with `org`, `repo`, `ref`, and the exact `sha`.

**Why:** In this workspace, GitHub-triggered production attempts were canceled before logs appeared, and Vercel rejected redeploying a canceled record. A later cancellation explicitly cited an unverified commit signature; a fresh exact-SHA deployment reached `READY` only after the user authorized that one-off bypass. The monorepo's successful manual build took about nine minutes, even though it made progress in the build events.

**How to apply:** Confirm the Vercel project, linked repository, branch, and exact remote SHA. If cancellation cites an unverified signature, ask before bypassing it. With authorization, create a new production deployment from that Git source with `forceNew=1`, then verify the ready state and public production alias. For this monorepo, allow roughly nine minutes and inspect `GET /v3/deployments/{id}/events` while it remains `BUILDING` rather than starting a duplicate deployment.
